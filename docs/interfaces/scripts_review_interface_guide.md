# 脚本检查界面说明

## 这个界面是做什么的

脚本检查界面是系统的风险审查台。

它适合用在两种情况：

1. 你已经有一份脚本，想检查有没有风险
2. 你想让系统给出一个“更安全的修订版本”

所以它不是用来“从零写脚本”，而是用来“审查现成脚本”。

## 这个界面能做什么

当前支持：

- 选择达人
- 输入审查主题
- 粘贴脚本内容
- 选择目标语言
- 选择国家
- 选择平台
- 选择分发方式
- 选择品类
- 输入品牌 ID
- 发起风险审查

审查完成后会显示：

- 风险报告
- 建议修订稿
- 命中证据
- 规则命中

## 左侧输入区怎么理解

### 达人选择

这里的作用主要是给审查过程提供达人上下文。

系统可以读取：

- 达人备注描述
- 风格提示词

这样做的好处是：

- 审查建议不会完全脱离达人风格
- 修订稿更贴近当前达人语气

### 审查主题

这是给系统一个“这份脚本在讲什么”的总结。

如果你不填，系统会尝试用脚本第一行做主题。

### 脚本内容

这是最核心的输入。

你可以把：

- 手写脚本
- 别人给的脚本
- 生成模块产出的脚本

直接贴到这里审查。

### 目标语言

影响审查语境与修订稿方向。

### 国家

决定按哪个市场来审查。

### 平台

决定平台规则范围。

### 分发方式

这个字段非常关键。

因为不同场景对 disclosure 和广告表述要求不同：

- `Organic Post`
- `Branded Content`
- `Paid Ads`

### 品类

决定风险重点。

例如：

- `electronics` 更偏一般广告表达审查
- `beauty`、`health_supplement` 这类会更容易命中敏感功效类风险

### 品牌 ID

当前是品牌上下文字段，便于后续扩展品牌规则和品牌知识库。

## 右侧几个结果区分别看什么

### 风险报告

这是总览区。

它会告诉你：

- 当前状态
- 整体风险
- 一共有多少条问题
- 风险摘要

这是你第一眼应该看的区域。

### 建议修订稿

这是系统基于原稿和风险问题，自动给出的更安全版本。

如果你想快速改稿，先看这里。

### 命中证据

这里显示知识库检索回来的证据块。

它的作用是告诉你：

- 系统不是乱判
- 它参考了哪些文档片段
- 这些文档来自什么来源

### 规则命中

这里显示的是本地规则引擎命中的硬规则。

这部分和“风险报告”不完全一样。

简单理解：

- 风险报告：综合判断结果
- 规则命中：底层硬规则明细

## 它背后的真实流程

脚本检查的后端流程大致是：

1. 接收脚本内容
2. 做脚本文本清洗
3. 确定审查范围
4. 去知识库检索证据
5. 本地规则引擎做规则命中
6. LLM 综合生成风险报告
7. LLM 输出建议修订稿

接口：

- `POST /scripts/review`

服务层：

- [scripts.py](/Users/bailumac/Developer/my-grad-proj/backend/services/scripts.py)

## 它和图书馆的关系

这个界面和图书馆关系很强。

因为审查时会从知识库中取证据。

如果图书馆里的资料不完整，脚本检查会出现：

- 证据不足
- 审查过于泛化
- 引用来源少

所以想让脚本检查更可靠，图书馆资料必须持续维护。

## 数据流动

脚本检查的数据流是：

1. 前端把脚本发给 `/scripts/review`
2. 后端清洗脚本
3. 结合国家 / 平台 / 分发方式 / 品类做范围解析
4. 去 Qdrant 检索知识库证据
5. 本地规则引擎做规则命中
6. 输出风险报告
7. 输出建议修订稿

## 你最适合怎么用它

最适合的 3 种用法：

- 先在脚本生成界面出一稿，再来这里单独复核
- 外部团队给了脚本，你直接贴进来做审查
- 品牌合作内容上线前，先做一轮风险排查

## 当前使用提醒

这个页面当前是“文本输入型”的。

如果后续页面出现语音入口提示，也不代表现在已经完整接通语音审查链路。当前主流程仍然是粘贴文本审查。

## 这个界面的定位总结

脚本检查界面是内容上线前的风险闸门。

它的价值不在于替你写内容，而在于帮你发现风险、给出证据、顺手产出一版更安全的修订稿。
